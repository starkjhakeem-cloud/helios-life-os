# HELIOS — Technical Talking Points

Interview prep for engineering roles. This file focuses on the actual architecture, backend/API flow, trade-offs, limitations, and the next roadmap.

---

## Opening Pitch

"HELIOS is a full-stack iOS productivity app built with React Native and Expo on the frontend, and FastAPI with PostgreSQL on the backend. It demonstrates a complete product flow: auth, persistent storage, AI-assisted planning, analytics, local notifications, and a documented deployment path."

---

## Architecture Overview

### Mobile
- React Native 0.83 + Expo SDK 55
- File-based routing with Expo Router under `mobile/src/app/`
- 11 Zustand stores for domain state
- Persisted stores: `useAuthStore` and `useSettingsStore`
- Shared `apiClient` with 15-second `AbortController` timeout
- Authentication via `Bearer <JWT>` header

### Backend
- FastAPI on Python 3.12
- One router per resource: auth, goals, tasks, analytics, dashboard, agents, AI, conversations, reminders, settings, health
- `get_current_user` dependency on every protected route
- Pydantic v2 request/response validation
- SQLAlchemy 2.0 ORM with typed `Mapped[]` columns

### Database
- PostgreSQL 16
- 6 Alembic migrations in `backend/alembic/versions/`
- Main tables: `users`, `goals`, `tasks`, `conversations`, `conversation_messages`, `reminders`, `user_preferences`
- FK constraints with `CASCADE` and `SET NULL` rules
- `user_preferences` uses `user_id` as both PK and FK for a 1-to-1 relationship

## System Design Questions

### "Walk me through the architecture."

The app is a three-tier system:

1. **Frontend** — React Native app with Expo Router and Zustand. It persists auth and preferences, and fetches fresh domain data for goals, tasks, AI, and reminders.
2. **API** — FastAPI service with typed request/response models. Every protected endpoint validates the JWT and enforces `user_id = current_user.id`.
3. **Data** — PostgreSQL with schema migrations. The backend is containerized and starts by applying migrations.

### "How does authentication work?"

- Signup hashes passwords with bcrypt and stores only `hashed_password`.
- Login verifies bcrypt and returns a JWT.
- JWT includes `sub`, `exp`, and a `type` claim.
- `get_current_user` decodes the token and loads the user from the DB.
- Auth routes are rate-limited to prevent brute force.

### "How does state management work?"

- Each Zustand store has data, `isLoading`, `isMutating`, `error`, and `reset()`.
- Only auth and settings are persisted to AsyncStorage.
- All other stores are in-memory and reset on logout.
- Logout clears all domain stores before removing credentials.

### "Why Zustand instead of Redux?"

- Lower boilerplate.
- Strong TypeScript support.
- A natural fit for per-domain mobile state.
- No need for a large global reducer layer in this app.

## AI Architecture

### Provider abstraction

- `AIProvider` is an abstract base class in `backend/app/ai/base.py`
- `get_ai_provider()` returns either `MockAIProvider` or `OpenAIProvider`
- The routers only call provider methods; they do not depend on the implementation

### How to switch providers

- Default: `AI_PROVIDER=mock`
- Real mode: `AI_PROVIDER=openai` and `OPENAI_API_KEY`

This design means the same API routes work in demo mode and real mode without code changes.

## Database Design

### Key tables

- `users` — UUID PK, email unique, bcrypt hash
- `goals` — FK `user_id` CASCADE
- `tasks` — FK `user_id` CASCADE, `linked_goal_id` SET NULL
- `reminders` — FK `user_id` CASCADE, optional `goal_id`/`task_id` SET NULL
- `user_preferences` — PK = `user_id`, FK CASCADE
- `conversation_messages` — stores message metadata as JSON text

### Design tradeoffs

- UUID strings are generated by the app instead of serial IDs.
- Date fields are stored as ISO 8601 strings to simplify serialization.
- `user_preferences` is separate to keep the user model lean.

## Scaling and Performance

### Current bottlenecks

- Connection pool is small: `pool_size=5, max_overflow=0`.
- Analytics runs live aggregation on every request.
- AI calls are synchronous and could block workers under concurrency.
- Task/goal lists have no pagination.

### Practical scaling upgrades

- Increase DB `max_overflow` and use a connection pool strategy.
- Add caching or materialized views for analytics.
- Make AI endpoints async or move them to a task queue.
- Add pagination to list endpoints for large data sets.

## Interview Talking Points

### Strengths

- Full-stack ownership from mobile UI to backend API to database schema.
- Production-grade patterns: typed validation, JWT auth, rate limiting, ownership enforcement.
- A clean AI integration layer that separates interface from provider.
- Documentation and demo materials are included.

### Honest limitations

- No automated tests.
- JWT stored in AsyncStorage instead of secure storage.
- No refresh tokens.
- Default AI provider is a deterministic mock.
- No App Store/TestFlight release yet.
- Date input controls are plain text fields.

### Good answers to expected questions

**If asked about App Store readiness:**
"The app is configured for Expo EAS builds, but it has not been submitted to TestFlight yet. The remaining work is release readiness, not core functionality."

**If asked about AI:**
"The AI implementation is complete, but for portfolio demos I use the mock provider because it is predictable. The OpenAI implementation is activated with environment variables."

**If asked about security:**
"Every protected API query is scoped to `current_user.id`, and auth routes use rate limiting. The next security step is moving JWT storage to secure storage and adding refresh tokens."
